# Audio DSP and plugin engineering principles

These are the Oiko engineering rules for plugins built on NicePlug Community and egui. Use them as design requirements and review criteria. They do not claim that every host or platform has been tested. The rules target NicePlug 0.4.0, nice-plug-egui 0.5.0 and egui 0.36.1. The committed lockfile and the patch register give the exact sources.

## Ownership and architecture

1. **Separate algorithms from hosting.** A DSP or core crate accepts plain values, slices and explicit configuration. It imports neither NicePlug nor egui. A plugin crate translates host buffers, note events, transport, parameter changes, latency and persistence into calls to the core crate. Name each module after the job it does, such as `particle_adapter`, `mts_client`, `parameter_controls` or `display_data`. Split a larger module into concrete parts such as parameter definitions, persisted state, editor interaction, history and rendering. Keep product-specific implementations in the product. Consumers import an internal API from the crate that defines it. When you move an API, update its consumers instead of keeping compatibility wrappers or re-exports.
2. **Give each thread its own state.** The audio thread owns live processing state. The UI thread owns interaction, painting and resize requests. Worker threads own parsing, disk access, library scanning, and calls to external services with unknown execution time. Closing the editor must not stop processing.
3. **Share mechanisms, keep product identity local.** Typography, DPI conventions, window adapters, the common palette and generic numerical algorithms each have one implementation. Each product defines its own parameter IDs, DSP topology, layout, tuning policy and interaction model. Extract an existing mechanism when a second product needs it. Product integrations such as ODDSound MTS-ESP stay in the plugin that uses them or in that plugin's core crate. The shared DSP, UI and host crates must not require those libraries or start their services. If two products need the same integration, put it in a separate crate that each consumer depends on explicitly. A patched source in the central `vendor/` directory is not a dependency of every plugin.
4. **Document lifecycle obligations.** Document what prepare or activate, reset, process, reconfigure and destroy each do. Allocate memory and create workers before audio starts. Reset clears only prepared state. Shut down and join workers, drop the last `Arc` references and destroy large resources outside processing callbacks.

## Real-time guarantees

5. **Bound every audio operation.** Process and parameter-flush paths must not allocate or free heap memory, wait on a mutex or condition variable, spin until an operation succeeds, sleep, call the filesystem or network, create threads, format strings, log or access graphics. Preallocate for the largest supported block, FFT, voice count, event queue and scratch requirement. A control that the host cannot automate can still change during processing, so it follows the same rules.
6. **Prepare everything before processing.** Precompute FFT plans, windows, interpolation tables and frequency lookup data during activation. Switch to a prepared configuration without dropping the old one on the audio thread. Use explicit FFT scratch buffers. Do not assume that a backend needs no scratch space.
7. **Pick the channel that fits the data.** Use atomic scalars for independent meters. Use a coherent bounded snapshot for a batch of related parameters or a tuning table. Use a bounded SPSC queue for ordered events, and define what happens when it is full or empty. The audio thread makes one attempt. On contention it keeps the last valid state, and it never waits for the editor. Keep communication values, flags and memory ordering behind the protocol API. Route internal parameters by named identities, not by numeric conventions. Document the writers, readers and memory ordering. Drop old resources only on a non-audio thread.
8. **Treat display data as disposable.** Decimate audio-to-UI display data before publishing it. Repaint at the UI rate. Lost meter data or a closed editor cannot change the sound. Label snapshots built from several scalars as approximate, because a collection of atomics does not form a coherent frame.
9. **Audit native code too.** Rust ownership and an allocation guard do not prove that a C or C++ dependency or an external runtime is real-time safe. Record the call path and its threading assumptions. Keep native dynamic loading, registration, ownership arbitration and master publication out of the process callback.
10. **Test rare transitions.** Allocation checks must cover resolution and quality changes, new maximum block sizes, state restore, silence, note floods and transport changes, not only steady playback. Memory safety tools and sanitizers add to numerical and host tests. Neither replaces the other.

## Signal and musical correctness

11. **Specify units and numerical domains.** Names and API docs distinguish Hz, seconds, samples, cents, semitones, linear gain, decibels and normalized parameters. Check that values are finite where they arrive from the host, saved state or files. Define the behavior for overflow, denormals, silence floors and invalid configurations.
12. **Decide where the signal must stay continuous.** Smooth continuous controls that need it, in a domain that suits each control. Do not smooth discrete selections by default. Document bypass, reset, transients when quality switches, latency changes, tail length, and whether a change needs a crossfade or a host restart.
13. **Honor event timing.** Carry the sample offsets that the host supplies for notes, automation and supported modulation through the host adapter into processing. Do not round them to host-block boundaries. Instrument triggers and envelope starts take effect at their specified sample. Document whether a parameter transition starts at its timed event or is centered on it. Centered smoothing needs advance knowledge of the event or lookahead. Report any latency it adds to the host. Centered smoothing must behave the same across host-block boundaries. Precise event timing does not require an instant audible jump. If the DSP updates at a coarser rate, such as once per spectral frame, document that rate separately from event delivery and reported latency. Verify timing with events inside blocks and with different block sizes, including a note and a parameter change at the same sample. Do not invent automation detail finer than the host supplies. State what happens with stopped transport, sample-rate changes, loop or seek, and offline rendering. Inton's MTS publication is a documented exception. It publishes at a wall-clock control rate, so its tuning updates are not sample-accurate.
14. **Measure quality and cost.** Where they apply, test impulse and DC response, frequency response, reconstruction, aliasing, modulation continuity and deterministic output. Benchmark typical and worst-case sample rates, block sizes, channel and voice counts, and configurations. Record the test environment and the numerical tolerances. Optimize bottlenecks you have measured, and keep the reference implementations and their tests.

## Host contracts and UI

15. **Keep sessions compatible.** Plugin IDs, parameter IDs, enum values and ranges, serialization keys and state versions are public contracts. Validate the complete state before applying any of it, and reject malformed input without losing the current project. Check that stream lengths fit the platform's size limits. Grow input buffers fallibly as data arrives. A size limit that one product needs must not become a limit for the whole framework. Keep support for partial reads and writes. Tell the host when a state restore changes parameter values.
16. **Use host gestures correctly.** Begin, set and end each parameter gesture through NicePlug. End any open gesture when the editor closes. Local undo must not also trigger host undo. Capture only the shortcuts that the editor handles.
17. **Distinguish scale from DPI.** Layout uses logical points. User zoom and monitor backing scale are different values. On macOS, the shared adapter converts between AppKit points and pixels. On Linux and Windows, the backend does the conversion. Queue resizes until after the egui UI pass so that callbacks do not re-enter. Validate a restored zoom value and fall back to a usable default.
18. **Use the shared typography roles.** Install fonts when the editor is created or the theme changes, and ship the font licenses with them. Use the four sizes in `oiko_ui::typography` (`TEXT_SMALL`, `TEXT_BODY`, `TEXT_HEADING` and `TEXT_TITLE`), including in custom painting, and do not add more. Check text clipping, hit targets, keyboard navigation and both themes at every supported zoom step. Repainting must not depend on audio activity.

## Maintainability and release quality

19. **Make builds reproducible.** Commit the root lockfile, declare an accurate minimum supported Rust version, keep the reviewed dependency patches, and publish the complete workspace source. In each workspace member's Cargo metadata, declare its dependency role, its product where it has one, and its integration dependencies. The boundary checks then cover each new crate without extra setup. Build and test core crates without graphics. A change must pass formatting, Clippy with no warnings, the dependency boundary checks and representative integration tests.
20. **Patch once and plan the removal.** Each patch has one maintained source, a recorded upstream revision, a minimal diff, the original notices, a regression test and a removal criterion. Keep general fixes apart from product migrations and from vendoring or packaging choices. Never imply that upstream has accepted a patch.
21. **Report failures outside the audio thread.** Report worker, build and load errors with the operation and input that failed. Limit the size of untrusted files, saved state and native parser inputs. Document the invariants of `unsafe` code at the boundary where they apply. Do not silence lints across whole crates or modules.
22. **Record what you tested.** Unit tests do not show that an embedded window works in every host. Before a release, test CLAP and VST3 on macOS, Windows and Linux. Cover opening, closing and reopening the editor, multiple instances, state recall, resize, zoom and DPI changes, shortcuts, transport, suspension and offline mode. List the platform checks that are still open, and keep the known limitations documented.
